# Setup and owner checklist

Everything a maintainer can do is done. This page is the short list that only the owner can do,
in the order it unblocks the most. Nothing here needs a code change unless it says so.

## 1. Merge the open pull requests, in this order

One pull request per slice, stacked. Each base is the previous branch, so the order is fixed:

| Order | Repository | Pull request | Base | Why it is here |
| --- | --- | --- | --- | --- |
| 1 | `vivarium` | #1 Add the seven systems, the pinned manifest, and the umbrella checks | `main` | Everything else builds on the pins and the tool |
| 2 | `vivarium` | #2 Automate the system pin bump | #1 | Needs `npm run check` to exist |
| 3 | `vivarium` | #3 Add the banner, the README, and the generated system map | #2 | The README blocks are generated by the tool |
| 4 | `vivarium` | #4 Add the umbrella agent context | #3 | The context file links the README |
| 5 | `vivarium` | #5 Specify first-run setup, model access, context access, and the system work | #4 | Specs link the agent context |
| 6 | `vivarium` | #6 Add the timeline, the decision records, and the product brief | #5 | The brief and records are linked from the specs |
| 7 | `vivarium` | #7 Add the contributor, security, and issue templates | #6 | Final prose layer |
| 8 | `vivarium` | #8 Add the setup checklist and close the record | #7 | This page, and the last timeline entries |
| 9 | `vivarium` | #9 Replace the design brief with the canonical edition | #8 | The brief the rest of the docs explain, verbatim from the owner |
| 10 | `docs` | #4 Add vivarium to the synced sources | `main` | Independent of the stack; the next docs sync picks vivarium up |

Squash-merge each one; the ruleset allows squash only. After #1 lands, the required `check`
check exists for every later pull request, and after #2 lands the bump workflow can run.

## 2. Confirm the Actions setting

Already applied to this repository:

```
default_workflow_permissions = read
can_approve_pull_request_reviews = true
```

That second flag is the "Allow GitHub Actions to create and approve pull requests" setting the
bump workflow needs. If an organisation policy controls it, the repository setting is ignored:
check **Organisation settings → Actions → General → Workflow permissions** and allow it there,
or accept that the bump workflow fails to open its pull request and move the pins by hand with
`npm run sync` on a branch.

## 3. The dispatch token, so a system's push wakes the umbrella (optional)

Without this, the umbrella still catches every move on its six-hour schedule. With it, a push to
a system's `main` opens the bump pull request within a minute.

1. Create a fine-grained token or a GitHub App installation limited to `Vidoxlabs/vivarium`, with
   **Contents: read** and the permission the dispatch API needs (**Metadata: read** for a
   fine-grained token; **Actions: write** if you dispatch workflows instead).
2. Store it as an organisation secret `VIVARIUM_DISPATCH_TOKEN`, scoped to the seven system
   repositories.
3. Open one pull request per system adding
   [`templates/notify-vivarium.yml`](templates/notify-vivarium.yml) as
   `.github/workflows/notify-vivarium.yml`, following that repository's own rules.

With no secret, the template prints one line and exits 0. Nothing breaks.

## 4. The bot token, only if the dispatch route is not enough (optional)

Pull requests opened with `GITHUB_TOKEN` do not start `pull_request` workflows, so the bump
workflow dispatches `ci.yml` on the branch by hand to land the required `check` status. That is
the tested path and it needs no token.

If it turns out not to satisfy the required check (the check may stay "expected" on a required
context that a dispatch names differently), create an organisation or repository secret
`VIVARIUM_BOT_TOKEN` for a fine-grained token with **Contents: write**, **Pull requests: write**,
and **Actions: write** on `Vidoxlabs/vivarium`. The workflow uses it when present and falls back
to `GITHUB_TOKEN` when it is not, so adding it needs no code change.

## 5. A maintainers team, so CODEOWNERS can do its job

`.github/CODEOWNERS` names an organisation team and is commented out, because no team exists
yet. Either:

  `* @Vidoxlabs/<team>`, and optionally turn on "Require review from Code Owners" in the
  ruleset; or
- leave it as it is. The ruleset does not require a code-owner review, so nothing is blocked.

## 9. The product brief

`docs/vision/design-brief.md` is now the owner's second edition, verbatim, with only the required

## 10. Make the seven system checks required, once the first bump is green

The `systems (…)` jobs are advisory today, so a bump pull request could merge with a red system.
The owner's rule: turn them on only after the first pin-bump run is green on all seven.

When that run exists, run this, replacing `NNNN` with the ruleset id (currently `28075499`):

```bash
gh api -X PUT repos/Vidoxlabs/vivarium/rulesets/NNNN --input - <<'JSON'
{
  "name": "main",
  "target": "branch",
  "enforcement": "active",
  "conditions": { "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] } },
  "rules": [
    { "type": "deletion" },
    { "type": "non_fast_forward" },
    { "type": "required_linear_history" },
    { "type": "pull_request", "parameters": {
        "required_approving_review_count": 0,
        "dismiss_stale_reviews_on_push": true,
        "require_code_owner_review": false,
        "require_last_push_approval": false,
        "required_review_thread_resolution": true,
        "require_extra_approval_for_unattributed_changes": false,
        "allowed_merge_methods": ["squash"] } },
    { "type": "required_status_checks", "parameters": {
        "strict_required_status_checks_policy": true,
        "required_status_checks": [
          { "context": "check" },
          { "context": "systems (seed)" },
          { "context": "systems (capillary)" },
          { "context": "systems (myosotis)" },
          { "context": "systems (drosera)" },
          { "context": "systems (aestivation)" },
          { "context": "systems (bloom)" },
          { "context": "systems (trellis)" }
        ] } }
  ]
}
JSON
```

If a context name does not match exactly, the check stays "expected" forever and no pull request
can merge: read the job names off the first bump run's summary before running this.

## What this run already did

| Thing | State |
| --- | --- |
| Repository | public, MIT, default branch `main`, description and topics set |
| Settings | squash-only merge, squash title from the pull request title, blank squash body, auto-delete head branches, Issues on, Wiki and Projects off, Discussions off |
| Ruleset `main` | deletion blocked, non-fast-forward blocked, linear history required, pull request required (0 approvals, stale reviews dismissed, threads resolved), required status check `check`, squash the only merge method |
| Workflow permissions | read by default, Actions may create and approve pull requests |
| Submodules | seven, HTTPS, `branch = main`, `shallow = true`, `update = checkout` |
| CI | `check` (required) and the `systems` matrix, both green on every pull request head |
| Dependabot | not enabled for submodules; the reason and a ready snippet are in ADR-0001 |

## What is deliberately not done

- **No merges.** Every pull request is open for the owner.
- **No Dependabot.** It would open one pull request per submodule and fail the drift check; ADR-0001
  has the snippet and the extra job adopting it needs. The owner confirmed on 25 November 2026
  that the bump workflow stays the path.
- **No auto-merge on pin bumps.** The owner merges each bump pull request himself.
- **No org teams, secrets, tokens, or GitHub Apps.** They are on this page instead.
- **No website repository, and no local agent workspace touched.**
- **No pull requests in the seven system repositories.** The work they imply is listed, labelled
  `planned`, in [`docs/roadmap/system-work.md`](docs/roadmap/system-work.md).
